## 3. Baseline Benchmarks

### What Was Compared

Four compression approaches were benchmarked:

1. **Parquet+zstd (level 1)**: Standard production compression. Generated by `pq.write_table(table, path, compression='zstd')`.
2. **Parquet+zstd (level 19)**: Maximum zstd compression. Generated by `pq.write_table(table, path, compression='zstd', compression_level=19)`.
3. **OpenZL Parquet Profile**: `zli compress file.parquet --profile parquet --train-inline`. Compresses the entire Parquet file as one `.zl` blob. Requires canonical Parquet (uncompressed, PLAIN encoding, no dictionary).
4. **OpenZL SDDL/PBL**: Custom approach where numeric column data is extracted into a flat binary format (PBL) with an SDDL schema describing the column layout. Each column becomes an independent compression stream.

### Preparing Canonical Parquet for OpenZL

The OpenZL Parquet profile requires specific Parquet settings:

```python
import pyarrow.parquet as pq
pq.write_table(table, "output_openzl_ready.parquet",
               compression='NONE',
               use_dictionary=False,
               write_statistics=False)
```

Without these settings, `zli` will error with "Found compressed chunk!" or fail on non-PLAIN encodings.

### Running the Benchmark

```bash
source nyx/.venv/bin/activate
python parquet_experiments/benchmark_openzl.py
```

### Baseline Results

Results stored in `parquet_experiments/results/comparison_comprehensive.json`:

|---|---|---|---|---|

## 4. Phase A: Per-Column Independent Compression

### Motivation

The whole-file OpenZL approaches produce a single `.zl` blob that requires full decompression to access any data. For queryability (column pruning), each column must be independently decompressible.

### Hypothesis

The SDDL approach already creates independent compression streams per column inside one `.zl` frame. If we split these into completely separate `.zl` files (one per column), the total compressed size should remain close to the whole-file result.

### Step 1: Extract Per-Column Binary Files

For each numeric column, extract the raw values as a flat binary file:

```python
import pyarrow.parquet as pq
import pyarrow.compute as pc
import numpy as np

table = pq.read_table("parquet_experiments/data/numeric_heavy_none.parquet")

# For each numeric column:
col = table.column("timestamp")
casted = col.cast(pa.int64())  # for timestamps
filled = pc.fill_null(casted, 0)
arr = filled.to_numpy(zero_copy_only=False)
arr = arr.astype(np.dtype("<i8"))  # little-endian int64
arr.tofile("parquet_experiments/per_column_experiment/numeric_heavy/timestamp.bin")
```

The full extraction script creates `parquet_experiments/per_column_experiment/<dataset>/<column>.bin` for all numeric columns.

### Step 2: Compress Each Column Independently

Each column is compressed with the matching LE profile:

```bash
ZLI=$(ls -t nyx/openzl/cachedObjs/*/zli | head -1)

# INT64 columns (8 bytes per value):
$ZLI compress timestamp.bin --profile le-i64 --train-inline --output timestamp.zl --force

# INT32/FLOAT columns (4 bytes per value):
$ZLI compress temperature.bin --profile le-i32 --train-inline --output temperature.zl --force

# INT16 columns (2 bytes per value):
$ZLI compress status_code.bin --profile le-i16 --train-inline --output status_code.zl --force

# BOOL columns (1 byte per value):
$ZLI compress is_returned.bin --profile serial --train-inline --output is_returned.zl --force
```

Profile selection by Parquet physical type:
- `INT64`, `DOUBLE`, `TIMESTAMP` → `--profile le-i64`
- `INT32`, `FLOAT` → `--profile le-i32`
- `INT16` → `--profile le-i16`
- `BOOLEAN` → `--profile serial`

### Step 3: Verify Round-Trip

```bash
$ZLI decompress timestamp.zl --output timestamp_rt.bin --force
md5 timestamp.bin timestamp_rt.bin
# MD5 hashes must be identical — lossless compression
```

Verified: all columns decompress to bit-for-bit identical data.
Decompression speed: ~1,000-1,100 MB/s.

## 5. String Column Support

### The Challenge

OpenZL's LE profiles work on fixed-width numeric data. String columns are variable-length (BYTE_ARRAY in Parquet). The `serial` profile treats data as raw bytes but is extremely slow on large string data (>600s timeout on 44 MiB).

### String Column Characteristics (mixed_type)

| Column | Values | Unique | Avg Length | Raw Size |
|---|---|---|---|---|
| product_name | 2,000,000 | 500 | 19.3 chars | 44.4 MiB |
| shipping_country | 2,000,000 | 30 | 2.0 chars | 11.4 MiB |

Both columns have very low cardinality, making dictionary encoding highly effective.

### Approach: Dictionary Encoding + OpenZL

Instead of compressing raw string bytes, we:
1. Build a dictionary of unique values
2. Replace each string with its dictionary index (uint8 or uint16)
3. Compress the index array with OpenZL LE profile
4. Store the dictionary as a small uncompressed blob

```python
# Build dictionary
unique_values = sorted(set(values))
dict_map = {v: i for i, v in enumerate(unique_values)}

# Choose index width by cardinality
if num_unique <= 255:
    indices = np.array([dict_map[v] for v in values], dtype=np.uint8)
    profile = "serial"  # byte-level
elif num_unique <= 65535:
    indices = np.array([dict_map[v] for v in values], dtype=np.uint16)
    profile = "le-i16"
else:
    indices = np.array([dict_map[v] for v in values], dtype=np.int32)
    profile = "le-i32"

# Save indices and compress with OpenZL
indices.tofile("product_name_dict_indices.bin")
# Then: zli compress product_name_dict_indices.bin --profile le-i16 --train-inline --output product_name_dict_indices.zl
```

### String Compression Results

| Column | Method | Compressed Size |
|---|---|---|
| product_name | Parquet dict + zstd | 2.16 MiB |
| product_name | **OpenZL dict + LE** | **2.04 MiB (+5.8%)** |
| shipping_country | Parquet dict + zstd | 1.10 MiB |
| shipping_country | **OpenZL dict + LE** | **0.92 MiB (+16.8%)** |
| **Combined** | **Parquet+zstd** | **3.27 MiB** |
| **Combined** | **OpenZL** | **2.95 MiB (+9.5%)** |

### Why This Works

Parquet's own string handling is already dictionary-based: it builds a dictionary page, then stores RLE-encoded indices. Our approach is equivalent but uses OpenZL's ACE model instead of zstd to compress the index array, achieving better compression on the integer sequences.

### Approaches That DON'T Work

- **Raw BYTE_ARRAY with `serial` profile**: Timed out after 600s on 44 MiB. The serial profile treats every byte individually — too many symbols, too slow for training.
- **Separated lengths + data**: The data portion (36.8 MiB of concatenated strings) has the same serial profile problem.

## 7. Key Findings

1. **Per-column independent compression loses NOTHING**: Compressing each column as a separate `.zl` frame produces total sizes 2-6% *better* than whole-file compression. Each column gets a fully optimized model.

2. **Queryability is feasible**: Since each column is an independent `.zl` frame, a reader can decompress only the columns a query needs. Column pruning works.

3. **String handling via dictionary encoding**: Low-cardinality strings (the common case in analytics) compress well when dictionary-encoded first, then compressed with OpenZL LE profiles. OpenZL beats Parquet+zstd by 6-17% on dictionary indices.

4. **Decompression is fast**: ~1,000 MB/s, verified via `zli decompress`. Round-trip is bit-for-bit lossless (verified via MD5).

5. **Training is the bottleneck**: `--train-inline` takes 15-250 seconds per column depending on size. This is a one-time cost. Columns can be trained in parallel across CPU cores on servers with sufficient core counts.

### Important Notes

- `zli` training times vary by CPU. Results were obtained on Apple Silicon (M-series) with 14 cores.
- The `--train-inline` flag performs model training as part of compression. For production use, separate `zli train` and `zli compress --compressor` steps allow reusing models.
- The OpenZL Parquet profile requires canonical Parquet files (no compression, no dictionary encoding, PLAIN encoding only). Regular Parquet files will cause `zli` to error.
- String compression results depend on cardinality. High-cardinality strings (e.g., UUIDs, free text) will not benefit from dictionary encoding and remain an open problem for OpenZL.
